🔴 Critical Issues — Must Fix Before Demo
C-01 Python crash: date variable shadows datetime.date module inside add_diagnosis CRITICAL ▶
Problem
In the add_diagnosis route (app.py ~line 2045), the local variable date = clean_record_field(request.form["date"]) shadows the date class imported from Python's datetime module. Any code within that scope that later calls date.today() will crash with AttributeError: 'str' object has no attribute 'today'.
Why It's a Problem
The function calls auto_generate_bill(..., date, ...) and inside build_doctor_password further upstream uses date.today().year. If any downstream function in the call chain uses date.today(), the app crashes silently for every doctor who saves a diagnosis — i.e., the core clinical workflow breaks.
Failing Case
Doctor opens a patient's consultation, fills diagnosis + prescription, clicks Save → 500 Internal Server Error.
Fix
# Change the local variable name from 'date' to 'consult_date'
consult_date = clean_record_field(request.form["date"])
# ...
auto_generate_bill(patient_id, doctor_id, consult_date, ...)
# Also update all references in the same function to consult_date
C-02 Credentials exposed in OS process list — authenticate_user passes password as CLI argument CRITICAL ▶
Problem
subprocess.run([exe_path, username, password], ...) passes the plaintext password as a command-line argument. On Linux/Windows, any user on the same machine can read running process arguments (ps aux / Task Manager) and see the password.
Why It's a Problem
All role credentials — Receptionist and all Doctor accounts — are permanently compromised to anyone with OS-level access. This is a known security anti-pattern that fails any security review.
Failing Case
Any OS user runs ps aux | grep auth.exe during login and sees: auth.exe reception admin123
Fix
# Option A (Recommended): Do auth in Python directly, bypass C exe
def authenticate_user(username, password):
    for account in read_user_accounts():
        if account["username"] == username and account["password"] == password:
            return {"username": username, "role": account["role"], "doctor_id": str(account["doctor_id"])}
    return None

# Option B: Pass credentials via stdin to auth.exe
result = subprocess.run([exe_path], input=f"{username}\n{password}\n",
                        capture_output=True, text=True, cwd=BASE_DIR)
C-03 Race condition: concurrent appointment booking can cause double-booking the same slot CRITICAL ▶
Problem
appointment.c:bookSlot() reads all appointments, checks slot availability, then appends a new booking — but uses two separate file operations with no locking. Two concurrent booking requests for the same slot can both pass the availability check before either writes, resulting in two appointments for the same doctor+date+time slot.
Why It's a Problem
In a real clinic with a receptionist + the Python Flask dev server handling multiple requests, this is a real risk. Two patients get booked for the same slot; the doctor sees a double appointment; billing is confused.
Failing Case
Two receptionists both open the appointment page for Dr. Arun Kumar at 08:30 AM, both see "Available", both click Book within milliseconds. Both bookings go through.
Fix
# In appointment.c bookSlot(), use file locking:
#include <fcntl.h>
// At start of bookSlot:
int lockfd = open(APPOINTMENT_FILE, O_RDWR);
flock(lockfd, LOCK_EX);  // exclusive lock
// ... do read-check-write ...
flock(lockfd, LOCK_UN);
close(lockfd);

# OR in Python, use a threading.Lock() around run_appointment_command("book",...)
import threading
_appt_lock = threading.Lock()
def run_appointment_command(*args):
    with _appt_lock:
        ...
🟠 High Priority Issues
H-01 Past-date appointment booking is allowed with no validation HIGH ▶
Problem
The book_appointment route in Python and bookSlot() in appointment.c only check that the slot is "Available". Neither checks whether the appointment date is in the past. The C validDate() only checks format, not that the date is ≥ today.
Why It's a Problem
A receptionist (or tampered POST request) can create an appointment for yesterday. That appointment will immediately be marked "No-show" by expire_stale_consultations() on the next page load, creating confusing ghost records.
Fix
# In book_appointment route, add before calling run_appointment_command:
parsed_appt_date = parse_iso_date(appointment_date)
if not parsed_appt_date or parsed_appt_date < date.today():
    return redirect(f"/appointments?status_note=Cannot book for a past date")
H-02 Billing total field is stored from user input, not re-calculated — tamper risk HIGH ▶
Problem
create_bill_record() calculates a correct total server-side (doctor_fee + treatment_total + lab_total + medicine_total), and this is fine. However, old 13-field bill records parsed by parse_bill_line() read the stored total directly without re-verification. If someone manually edits billing.txt, a mismatched total is displayed and sent on the PDF.
Why It's a Problem
Bill PDFs may show a total that doesn't match line items. For a clinic, this is a legal/audit concern.
Fix
# In parse_bill_line(), after parsing, recompute:
bill["total"] = (bill["doctor_fee"] + bill["treatment_total"]
                 + bill["lab_total"] + bill["medicine_total"])
# This makes the system self-healing against manual file edits.
H-03 read_patients() silently drops patients whose records don't have exactly 10 fields HIGH ▶
Problem
if len(data) != 10: continue — if a patient record ever gets written with a mismatched number of pipe-separated fields (e.g., because a name or address contained a | that wasn't fully sanitized, or a trailing whitespace creates an empty 11th field), the patient becomes invisible to all Python-side lookups. They can still receive appointments from the C side.
Failing Case
Patient name "Dr. S|Kumar" (pipe slips through) → record has 11 fields → Python can't find patient → billing lookup fails → "Patient not found" even though they exist in the file.
Fix
# Use >= 10 instead of != 10 and truncate/pad:
if len(data) < 10:
    continue
# This tolerates extra fields while rejecting genuinely corrupt lines
H-04 Doctor status update uses a temp file (temp.txt) with a hardcoded path — multi-instance unsafe HIGH ▶
Problem
In doctor.c, updateDoctorStatuses() writes to Backend/data/temp.txt then renames it. If two status updates happen simultaneously (e.g., receptionist and doctor both updating at once), both processes write to the same temp.txt, and whichever rename() runs last will overwrite the other's full doctors file — potentially losing a doctor's update or corrupting the file.
Failing Case
Receptionist sets Dr. A → Unavailable at the same moment Dr. B updates his own status → Dr. A's change is lost; doctors.txt is now the state from whichever process finished last.
Fix
// Use a unique temp filename per process:
char temp_path[256];
snprintf(temp_path, sizeof(temp_path),
         "Backend/data/temp_%d.txt", getpid());
// Then rename(temp_path, DOCTOR_FILE)
// Even better: use file locking before the read-modify-write cycle
H-05 Patient registration form has no server-side validation for required fields (name, gender, department) HIGH ▶
Problem
The register action in the reception route validates phone and age, but does not check for empty name, gender, department, or symptoms fields. If those are blank (e.g., HTML form bypass via curl), a patient is registered with empty critical fields. The C module's addPatient() catches empty name/phone/department, but its error output (Error|InvalidPatientData) causes the Python side to silently fail the else branch and show a generic error — no user-friendly message.
Fix
# In the 'register' action block, add:
if not name:
    show_registration = True
    message = "Patient name is required."
elif not gender:
    show_registration = True
    message = "Gender is required."
elif not department:
    show_registration = True
    message = "Department is required."
🟡 Medium Priority Issues
M-01 Billing page is O(n²) — calls get_patient_billing_context() for every patient on every load MEDIUM ▶
Problem
billing_lookup = {str(patient["id"]): get_patient_billing_context(patient["id"]) for patient in patients} runs for every patient on every billing page load. Each get_patient_billing_context() call internally calls read_appointments() and read_bills() which re-read the files from disk. With 20 patients = 40 file reads per page load. At 200 patients = 400 file reads.
Fix
# Pre-load appointments and bills once, then pass them in:
all_appointments = read_appointments()
all_bills = read_bills()
billing_lookup = {
    str(p["id"]): get_patient_billing_context_from_cache(p["id"], all_appointments, all_bills)
    for p in patients
}
M-02 billing.c is a dead module — never called from Python; causes confusion MEDIUM ▶
Problem
The entire billing.c / billing.exe module is never invoked by app.py. All billing logic (creation, reading, PDF) is handled purely in Python. The C module writes bills in the old 13-field format, while Python now writes a 19-field format. If billing.exe is accidentally called or re-introduced, it will write incompatible data.
Fix
Either remove billing.c / billing.exe from the project or add a clear comment in common.h marking it as deprecated. Do not call it from anywhere.
M-03 serve.c / serve.exe is a dead module — the /serve route just redirects MEDIUM ▶
Problem
The /serve POST route does nothing but redirect with a message: "Queue movement is now doctor-driven." The serve.exe binary exists and works, but is never called. The serve button in the queue page is completely non-functional from the user's perspective — no feedback on which patient was served.
Fix
Either remove the Serve button from the queue UI, or implement the logic. If queue is doctor-driven (correct design), the button should not appear at all so receptionists don't keep clicking it expecting something to happen.
M-04 Diagnosis parsing skips data[2] (patient_id field) — silently misaligns if format ever changes MEDIUM ▶
Problem
In get_diagnosis_context(), the DIAGNOSIS output from diagnosis.c is: DIAGNOSIS|record_id|patient_id|doctor_id|date|diagnosis|prescription. The Python parser uses data[3] for doctor_id, data[4] for date — this is currently correct by skipping data[2] (patient_id). However, data[2] is never captured into the returned dict. If someone adds a field to the C output before patient_id, all fields silently misalign.
Fix
elif data[0] == "DIAGNOSIS":
    diagnosis.append({
        "record_id": data[1],
        "patient_id": data[2],   # ← explicitly capture
        "doctor_id": data[3],
        "date": data[4],
        "diagnosis": data[5],
        "prescription": data[6]
    })
M-05 No validation that payment_status is one of the allowed values when generating a bill MEDIUM ▶
Problem
payment_status = request.form["payment_status"].strip() is written directly to the billing file without validating that it is one of ["PENDING", "PAID", "WAIVED"]. A tampered POST request or a rogue client can inject arbitrary strings (e.g., PAID|fake|1000) which, due to the pipe delimiter, could corrupt the billing record.
Fix
ALLOWED_PAYMENT_STATUSES = {"PENDING", "PAID", "WAIVED"}
if payment_status not in ALLOWED_PAYMENT_STATUSES:
    payment_status = "PENDING"
M-06 Doctor dashboard shows empty queue if appointment date is today but doctor is marked Busy, not Free MEDIUM ▶
Problem
suggest_doctors_by_department() in doctor.c filters out doctors where current_status == "Emergency" but includes both Free and Busy. However, the queue module's findAvailableDoctor() requires current_status == "Free". This means walk-in queue assignments may silently assign to -1 (no doctor) when all doctors in a department are Busy but Available — causing token 7 in the current data (patient 13, doctor 2) to be valid, but a new walk-in would get doctor_id = -1.
Fix
Align the "suggest" logic in doctor.c and the queue assignment logic to use the same availability criteria. Document which status combinations allow queue assignment vs. appointment booking separately.
🔵 Low Priority Issues
L-01 Secret key falls back to a hardcoded default in production LOW ▶
Problem
app.secret_key = os.environ.get("HEALTHDESK_SECRET", "healthdesk-dev-secret") — if the environment variable is not set (which it won't be unless explicitly configured), every deployment uses the same hardcoded secret. Session cookies can be forged by anyone who knows this default.
Fix
secret = os.environ.get("HEALTHDESK_SECRET")
if not secret:
    raise RuntimeError("HEALTHDESK_SECRET env variable is not set")
app.secret_key = secret
# Or during development, log a warning and auto-generate:
import secrets
app.secret_key = secret or secrets.token_hex(32)
L-02 Passwords stored in plaintext in users.txt LOW ▶
Problem
users.txt contains reception|admin123 in plaintext. Anyone with file access to the server gets all credentials immediately.
Fix
Hash passwords with werkzeug.security.generate_password_hash when creating accounts and verify with check_password_hash during login. This alone would significantly raise the security baseline. (Requires moving auth fully to Python — which you should do anyway per C-02.)
L-03 MAX_APPOINTMENTS = 2000 — static array in C will crash silently beyond limit LOW ▶
Problem
appointment.c declares struct Appointment list[MAX_APPOINTMENTS] on the stack and silently stops reading at 2000 appointments. Any booking or reschedule beyond that limit silently fails — no error, no log. For a clinic running 20+ appointments/day, this is ~3 months of data.
Fix
Either increase the limit to 50000, allocate dynamically with malloc(), or — better — move to a circular/archiving model where completed appointments older than 90 days are moved to a separate archive file.
L-04 No CSRF protection on state-changing POST routes LOW ▶
Problem
All POST routes (book appointment, cancel, generate bill, etc.) have no CSRF tokens. While SESSION_COOKIE_SAMESITE="Lax" provides some protection in modern browsers, it is not sufficient for a medical application where actions have real consequences.
Fix
pip install Flask-WTF
# In app.py:
from flask_wtf.csrf import CSRFProtect
csrf = CSRFProtect(app)
# In every form template: {{ csrf_token() }} hidden input
